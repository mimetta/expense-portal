Every approved revision is retained. The spend report resolves each budget cell to the most recently approved revision containing that cell — so a segment's budget is assembled from several owners' revisions, each approved at a different time.

What changed from v1 — the revision is now keyed to the owner, not the segment:
  1. The editor shows your lines, grouped department → cat_l1 → cat_l2, spanning every department in your scope. The department dropdown is a filter, not the revision's identity.
  2. One draft per BO per fiscal year — not one per segment. The unique index changes accordingly.
  3. The CEO approves a cross-segment revision, and the banner says plainly that it is a partial view of each segment touched.
  4. The spend report must resolve budget per cell, to the latest approved revision containing that cell — no longer a clean per-segment lookup.
Carried over from v1, still binding:
  1. Approved figures stay live while a draft is edited — the report never reads a draft.
  2. Every revision retained, never overwritten.
  3. No self-approval, enforced at the database level.
  4. Rejection requires a note and returns the revision to draft with figures intact.
  5. Lines come from the categories table, so budget can only be set where requests can be filed.
  6. Entry ergonomics carry the feature — paste-a-row, fill-right, copy-last-year, arrow keys.
Open question this design surfaces:
  1. If two owners' scopes ever overlap on one cell, two revisions could claim it and the last approved would silently win. The state machine must refuse at draft creation and again at approval rather than resolve it — a database constraint can't express this.
